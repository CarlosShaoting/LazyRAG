## 3. 已确认问题

### F1 · P1 · #750 同步完成度评估阻塞当前服务 worker

**位置：** [runner.py:1674–1684](https://github.com/LazyAGI/LazyMind/blob/19126987ab8b6eb9e113e9d053bad6efb398609e/algorithm/lazymind/chat/engine/subagent/runner.py#L1674)，内部同步模型调用位于 1904–1906 行。

新增分支使所有没有必需输出槽的普通 SubAgent，以及最终文本命中 concern 词的任务，在 `async run_subagent_stream` 内直接执行 `_evaluate_completion()`。该函数最终调用 LazyLLM 的同步模型接口，其 HTTP 请求使用同步 `requests.post`。

这段调用没有 `await asyncio.to_thread(...)` 或异步模型客户端。模型等待、重试期间，同一个事件循环中的其他任务、流输出、停止请求处理都会被延迟。评估后的 cancel check 只能在请求返回之后执行，不能让等待期间的事件循环继续服务。旧代码的同步评估只出现在普通任务缺少声明产物的补救路径；本 PR 将这个问题扩展到正常成功、无产物的日常任务。

**确定性复现：** 给合法纯文本任务的评估模型注入 200ms 同步等待，同时启动 25ms 的 asyncio 定时器。PR head 上定时器实际等待 **216ms**，断言失败；相同用例在 main 上通过，因为该成功任务不会进入补救评估。

**影响：** 单个普通任务的完成检查可阻塞当前 worker，模型响应慢时放大为并发请求停顿、停止动作延迟和上游等待超时。这里没有把影响扩大描述为所有部署实例都会一起阻塞。

**建议：** 将评估放入保留任务上下文的线程执行或使用异步接口，设置评估时间预算；等待期间保持取消检查和必要的心跳。仅套 `to_thread` 还需要考虑后台请求的超时与停止后结果丢弃。

**验收：** 慢评估期间并发计时器/请求正常推进，取消能及时被处理，取消后不发布成功终态。

### F2 · P2 · #750 新成功路径仍以 `stream=False` 调用仅支持流式的模型

**位置：** [新增评估入口 runner.py:1674–1684](https://github.com/LazyAGI/LazyMind/blob/19126987ab8b6eb9e113e9d053bad6efb398609e/algorithm/lazymind/chat/engine/subagent/runner.py#L1674)，调用实现为 [1904–1906 行](https://github.com/LazyAGI/LazyMind/blob/19126987ab8b6eb9e113e9d053bad6efb398609e/algorithm/lazymind/chat/engine/subagent/runner.py#L1904)。

执行 Agent 使用的模型可以正常流式完成任务，但新增的必经评估调用 `llm.share(stream=False)`。例如 QwQ 只支持流式输出；这一要求可由[阿里云官方文档](https://help.aliyun.com/en/model-studio/stream)确认。供应商拒绝非流式请求后，异常被转换成 `completion_evaluation_failed`，已完成的合法纯文本任务变成 failed。

**与您的提交的关系：** #770 已把 `_generate_display_plan` 改为 `llm.share(stream={'_stream_sink': ...})`，既支持此类模型又防止后台输出进入用户流。这段修复仍在 PR 中，但新 completion 路径没有沿用同样的兼容方式。`stream=False` 本身是既有代码；新增回归在于本 PR 将其引入原先直接成功的正常任务路径。

**确定性复现：** 使用真实 `OnlineChatModule(source='qwen', model='qwq-plus')` 构造请求，HTTP 层用受控替身模拟供应商：非流式返回 400，流式可返回合法 JSON verdict。捕获到请求 `stream=[False]`，终态为 `failed / completion_evaluation_failed`。main 上相同已完成任务成功。本测试未请求真实付费模型，供应商约束由官方文档另行核验。

**建议：** 采用与 display-plan 一致的静默流式聚合方式，保持 JSON verdict 校验，并确保评估文本、reasoning 和 runtime events 不进入用户输出队列。

**验收：** 覆盖 Qwen 原生及 OpenAI-compatible 流式模型；合法纯文本任务成功，评估输出不外泄到任务正文。

### F3 · P2 · #750 恢复任务仅凭文件记录与类型就认定交付完成

**位置：** [runner.py:1651–1660](https://github.com/LazyAGI/LazyMind/blob/19126987ab8b6eb9e113e9d053bad6efb398609e/algorithm/lazymind/chat/engine/subagent/runner.py#L1651)，以及 `context.py` 新增的历史 artifact 读取。

新的 gate 合并持久化快照与本轮 artifact，只校验 slot 和 content type 就将 key 放进 `saved`。当 required keys 满足、最终文本不命中 concern 时，评估也会跳过。恢复快照里的 `file` 记录即使指向已经删除、清理掉或未恢复的本地文件，也会直接满足合同。

**确定性复现：** 构造恢复任务，声明 `document: file`，历史记录指向确定不存在的 `deleted.pdf`，本轮不生成文件。PR head 发布 `done / succeeded`。测试明确检查该路径不存在。main 中历史记录不会直接满足 saved keys，测试配置的否定补救评估产生失败，未把失效记录当作硬性成功证据。

**影响：** 用户或父任务看到成功，却无法取得应交付文件。这会在任务恢复或工作区文件清理后重现本 PR 原本要避免的“有完成状态、无真实产物”。

**建议：** 历史文件在计入完成证据之前，通过对应 artifact 存储/文件解析层验证可用性；`file_list` 验证所有必需文件，大文本/JSON 的磁盘 offload 引用同样处理。跨主机路径应通过既有解析/恢复机制验证，不能简单把所有远端引用都按本机路径拒绝。

**验收：** 存在且可读的恢复文件成功；缺失文件返回 `missing_required_artifacts` 或明确的恢复错误；文件列表和 offload 引用也有失效用例。
